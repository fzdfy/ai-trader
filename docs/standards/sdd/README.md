# 规范驱动开发（SDD）版本索引

本目录保存项目 SDD 的长期版本基线。每个版本文件都是自包含的流程标准，记录该版本的设计原则、阶段、产物、确认方式、完成条件和 Skill 路由。

## 当前版本

**当前版本：v3。**

新的非平凡变更默认使用 v3。`v1` 和 `v2` 是冻结的历史基线，只用于审计、历史理解、现有变更兼容和迁移参考，不接收新规则。

当本目录与旧流程说明、历史 Superpowers 文档或归档记录出现表述冲突时：

- 新变更以 v3 为准；
- 已归档变更保持原记录，不按 v3 重写；
- v2 到 v3 的行为差异以迁移文档为准；
- v1 只解释旧流程当时如何执行；
- v1 到 v2 的行为差异以迁移文档为准。

## 阅读顺序

### Agent 开始新变更

1. 阅读 [v3.md](./v3.md) 的变更分类和流程；
2. 阅读对应风险等级和变更类型；
3. L2 额外声明 `assurance`；
4. 按 v3 创建 proposal、能力增量、design、tasks 和 verification；
5. 只在当前步骤触发条件满足时加载一个专业 Skill。

### 维护者理解历史

1. 阅读 [v1.md](./v1.md)；
2. 阅读 [v1-to-v2.md](./v1-to-v2.md)；
3. 阅读 [v2.md](./v2.md)；
4. 阅读 [v2-to-v3.md](./v2-to-v3.md)；
5. 再阅读 [v3.md](./v3.md) 的当前规则。

### 排查版本冲突

1. 确认变更创建时间属于 v1、v2 还是 v3；
2. 新变更以 v3 为准；
3. 历史变更保持当时版本的记录；
4. 迁移差异查阅 `v1-to-v2.md` 或 `v2-to-v3.md`。

## 共享定义

### SDD

SDD 指从变更意图、行为规格、技术决策、实施任务到验证证据的可追溯开发方式。它约束“做什么、为什么、如何证明”，不要求每个需求生成相同数量的文档。

### 当前版本

标有 **当前** 的版本是唯一适用于新变更的流程标准。本索引当前指向 v3。

### 历史版本

历史版本是冻结在某一时点的完整流程快照。可以修复明显笔误，但不能把后续规则回填到历史版本中。

### 变更类型

`feature`、`bug`、`ui`、`refactor` 和 `hotfix` 描述变更的主要性质，决定完成证据模板，不单独形成五套流程。

### 风险等级

`L0`、`L1`、`L2` 描述变更对系统、安全、数据和用户的影响强度。风险等级覆盖变更类型；高风险 bug 或 UI 修复不能因类型简单而降低流程。

### L2 保证档位

`assurance: bounded | systemic` 只适用于 L2，决定独立设计评审是否需要实施前门禁。它不是风险等级，也不允许把 L2 降为 L1。

### 期望基线

基线说明正确行为从哪里获得，可能来自规格、不变量、问题记录、已确认视觉稿或明确的新目标。没有基线时不能把猜测直接当作 bug 修复。

### 唯一事实源

同一事实只定义一次。OpenSpec 管变更与行为规格，实施任务只在 `tasks.md` 维护，验证证据只在 `verification.md` 汇总；其他文档只链接或说明补充信息。

### 硬停

硬停是需要用户重新决策的边界，包括范围变化、新产品决策、认证权限、数据源、PIT、迁移、L2 保证档位变化、破坏性操作、新增依赖、计划外失败和新的视觉方向。

## 维护规则

1. 新规则只写当前版本及其迁移文档，不修改历史版本语义。
2. 版本结构保持一致，便于比较流程、产物和 Skill 矩阵。
3. 每个版本必须列明 Skill 的职责、输入、输出、触发阶段和状态。
4. 已归档的 OpenSpec 变更不因版本升级而重写。
5. 升级当前版本时，必须先增加新版本文件，再更新本索引和迁移记录。
