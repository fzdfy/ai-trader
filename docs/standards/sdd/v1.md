# SDD v1：完整重型规范驱动流程

## Status and Scope

| 字段 | 值 |
|---|---|
| 版本 | `v1` |
| 状态 | **历史，已冻结** |
| 生效截止 | 2026-11-26 |
| 当前版本 | 否，当前版本见 [README.md](./README.md) 与 [v2.md](./v2.md) |
| 适用范围 | 审计、历史理解、旧变更兼容和 v1→v2 迁移 |

本文记录 v1 的真实执行方式，而不是重新设计的理论流程。v1 的目标是让需求、长期标准、设计、任务、测试和归档均有明确记录。其主要假设是：文档越完整、确认越频繁，Agent 行为越可控。

v1 不适用于新变更。新变更默认使用 v2。

## Design Principles

### 全量可追溯

非平凡工作必须依次经过澄清、PRD、OpenSpec、技术设计、技术评审、视觉设计、确认、实施计划、任务、编码、测试报告、审查和归档。任何阶段都不能只存在于对话中。

### 多文档分层

OpenSpec 记录 proposal、capability specs、design 和 tasks；`docs/superpowers/specs` 记录完整技术方案；`docs/superpowers/plans` 记录实施与测试计划；`verification.md` 记录验证结果。

### 逐步确认

每个工作流阶段和每个 `tasks.md` 编号任务都是独立确认步骤。完成后必须停止，汇报变更、证据、风险和下一步，用户明确确认后才能继续。

### 双执行框架

OpenSpec 负责规格和任务结构，Superpowers 负责从 brainstorming、writing-plans、executing-plans 到 TDD、review 和 verification 的方法。Ponytail 和项目领域 Skill 作为补充。

### 安全优先

身份认证、数据源、PIT、回测、迁移和视觉变更不因改动规模小而降级。高风险设计必须经过独立评审，视觉变更必须经过用户确认。

## Change Classification

v1 没有正式的 `type`、`risk`、`baseline` 或 `visual` 元数据字段。变更实际通过以下方式处理：

| 实际工作 | v1 处理方式 |
|---|---|
| 新功能、多页面流程、权限或数据口径 | 必须包含 PRD-lite；大型需求增加完整 PRD |
| bug 修复 | 进入同一 OpenSpec 流程；若已有规格，仍重复记录 proposal、design、plan、tasks 和 verification |
| UI 修复或 UI 调整 | 只要影响可见状态就进入完整视觉门禁；技术设计和视觉设计仍分别执行 |
| 重构 | 仍需 OpenSpec、写作计划、TDD 或既有测试证据、审查和验证 |
| hotfix | 没有独立快速通道；仍按非平凡变更逐步确认和记录 |
| 小型明确修改 | 可以视为单个步骤，但只授权该步骤本身 |

v1 的问题不是没有区分工作性质，而是即使正确行为已经由规格、不变量或问题记录定义，也倾向重新建立完整文档链。

## Workflow

v1 的标准阶段如下。每个阶段都受“逐步确认门禁”约束。

| # | 阶段 | 主要方法 | 产物 | 完成条件 |
|---|---|---|---|---|
| 1 | 需求澄清 | `grill-with-docs`、`grilling`、`domain-modeling` | 术语、ADR、决策树、proposal 输入 | 设计树无未决分叉，术语和长期决策已落位 |
| 2 | 产品需求 / PRD | PRD-lite；大型需求使用完整 PRD | `proposal.md` 或独立 PRD | 用户、场景、成功指标、非目标和验收标准明确 |
| 3 | 需求分析 | `openspec-propose` 或 `openspec-continue-change` | proposal、capability specs | 能力边界和可验证场景完成 |
| 4 | 技术方案 | `brainstorming` | `docs/superpowers/specs/*-design.md` | 架构、接口、替代方案、失败模式和回滚完成 |
| 5 | 技术方案评审 | builder check、独立技术评审 | `design.md#Review Result` | 结论为 `approved`，阻塞项清零 |
| 6 | 视觉设计 | `oil-ui`、`ui-design` | 探索稿、桌面/移动、浅色/深色截图 | 四类视觉检查和用户确认完成 |
| 7 | 用户确认 | 用户逐步评审 | 阶段确认记录 | 用户只确认当前阶段，不授权后续阶段 |
| 8 | 实施与测试计划 | `writing-plans` | `docs/superpowers/plans/*.md` | 每个任务有文件、接口、失败测试、验证命令和预期结果 |
| 9 | OpenSpec 任务清单 | OpenSpec | `tasks.md` | 任务映射计划，`tasks.md` 成为唯一实施进度清单 |
| 10 | 编码前简化 | `ponytail` | 最小完整方案说明 | 删除不必要复杂度后再编码 |
| 11 | 编码实施 | `test-driven-development` 和项目领域 Skill | 代码、测试、任务证据 | 每个已确认任务取得 RED → GREEN |
| 12 | 测试报告 | 自动化和人工验收 | `verification.md` | 记录通过、失败、跳过、未覆盖和证据 |
| 13 | 编码后精简 | `code-simplifier` | 行为不变的精简改动 | 测试保持通过 |
| 14 | 最终检查 | `requesting-code-review`、`ponytail-review` | 审查结论 | 正确性、安全、数据风险和复杂度有结论 |
| 15 | 完成验证 | `verification-before-completion` | 最新完整命令输出 | 验证结果与测试报告一致 |
| 16 | 归档 | `openspec-verify-change`、`openspec-archive-change` | 已归档 change、同步后的主规格 | 用户单独确认归档后完成 |

### 逐步确认协议

1. 开始前说明本步名称、计划修改、预期测试和主要风险。
2. 等待用户明确确认。
3. 只执行该阶段或该编号任务。
4. 完成后立即停止并汇报产物、证据、风险和下一步。
5. 用户再次确认后才能执行下一步。

“确认视觉稿”“确认计划”“全部同意”和“继续”都只覆盖当次列出的内容，不授权后续步骤或整个需求。

### Superpowers 执行资产

- `.superpowers/sdd/<plan-basename>/progress.md` 记录执行账本。
- task brief、review package 和测试输出属于临时执行资产。
- `docs/superpowers/specs` 与 `plans` 是正式规划资产，不由生成器维护。

## Confirmation Model

v1 使用最强的逐步确认：

- 工作流阶段是独立确认步骤；
- `tasks.md` 的每个编号任务是独立确认步骤；
- 一个阶段产生多个可独立验收产物时，每个产物可能再次成为确认步骤；
- 范围变化、阻塞、方案偏差和新增依赖必须单独确认；
- 视觉稿确认、计划确认、测试通过和审查通过都不能自动触发归档；
- 只有用户单独确认后才能归档。

这种模型提供了较高的中途可见性，但会造成重复读取上下文、频繁中断和大量“继续”回合。

## Skill Routing Matrix

Status 含义：

- `required`：v1 标准流程中的必经能力；
- `conditional`：满足明确触发条件时必须使用；
- `optional`：可辅助工作，但不是主流程必经能力；
- `bootstrap`：v1 的框架级启动约束。

|---|---|---|---|---|---|---|
| `using-superpowers` | 建立“先检查 Skill、再行动”的启动规则 | 当前任务 | 选定流程 Skill | 会话开始 | v1 会话开始 | `bootstrap` |

## Quality Gates

### 需求与规格

- 非平凡变更必须有目标、范围、非目标、验收标准和行为场景。
- 新用户功能、多页面流程、权限和数据口径变化必须有 PRD-lite。
- 同一规则只在对应长期标准中定义一次。

### 技术方案

- 至少说明一个替代方案、取舍、失败模式、兼容性和回滚方式。
- 独立评审结论必须写入 `design.md#Review Result`。
- `changes-required` 未清零前禁止编写生产代码。

### 视觉

- 任何可见变更必须完成探索、截图和用户确认。
- 截图覆盖桌面/移动和浅色/深色。
- 不适用时必须在 proposal 写明原因。

### 实施

- `tasks.md` 是唯一实施清单。
- 行为代码必须先有失败测试，再实现到通过。
- 每个任务有对应 RED → GREEN 或静态检查证据。

### 验证与归档

- `verification.md` 记录通过、失败、跳过、未覆盖和环境阻塞。
- 完成声明前运行最新完整验证命令。
- 测试和审查通过不能自动归档。
- 用户单独确认后才能执行 OpenSpec archive。

## Known Costs and Failure Modes

### 已知成本

- 普通变更也生成完整技术设计、实施计划和 OpenSpec 产物。
- 同一事实在 proposal、specs、design、完整设计、计划、tasks 和 verification 中重复。
- 每个阶段和每个任务都需要确认，产生大量上下文重读。
- Superpowers 执行器要求 ledger、task brief 和 review package，普通小改也需要维护。
- 并行文档可能与 OpenSpec 或 `tasks.md` 演化不同步，导致事实冲突。

### 已知失败模式

- **重复计划漂移**：完整计划与 `tasks.md` 对同一参数或范围给出不同值。
- **确认疲劳**：用户为了推进任务反复回复“继续”，但每次仍需重新说明上下文。
- **框架缺口**：当前安装的 Superpowers 缺少部分被引用的子 skill 和辅助脚本，执行者需要手工补账本。
- **过度文档化**：简单 bug、已有规格的修复和视觉回归也承担完整项目级材料。
- **局部通过误报完成**：只运行任务测试而未运行最新完整命令时，不能代表变更完成。

## Version Relationships

- v1 是历史基线，不再接收新规则。
- v2 是本目录当前版本，面向新变更。
- v1 到 v2 的原因、路径映射、Skill 保留/降级和回滚见 [v1-to-v2.md](./v1-to-v2.md)。
- 已归档 OpenSpec change 保留 v1 时期的记录，不因 v2 发布而重写。
