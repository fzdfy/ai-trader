## Design Principles

### 事实只写一次

- OpenSpec 管变更、行为规格和任务；
- `design.md` 管技术与架构决策；
- `tasks.md` 是唯一实施清单；
- `verification.md` 是唯一验证证据汇总；
- `docs/superpowers/specs` 和 `plans` 只作为补充材料，不复制上述事实。

### 变更类型不是流程类型

`feature`、`bug`、`ui`、`refactor` 和 `hotfix` 只决定主要完成证据，不创建五套流程。所有变更共用 OpenSpec 的薄结构和同一套质量门禁。

### 风险等级不等于保证档位

风险等级描述影响是否严重；L2 保证档位描述需要哪种评审时序。`bounded` 不是低风险，也不是任何门禁的豁免。

### 评审时序匹配影响范围

局部、可回滚且不改变数据或契约语义的 L2 在实施后合并代码与风险评审；系统性 L2 必须保留实施前设计评审和实施后评审。

### 批量执行，边界确认

默认在规划和实施计划确认后连续执行低风险任务，只在决策、风险和验收边界停下。最终验收和归档仍然分开确认。

### 保留关键质量门禁

TDD、视觉门禁、完成验证、独立风险审查和归档确认不因流程变薄而取消。

## Change Classification

每个进入 v3 的变更记录以下元数据：

```text
type:      feature | bug | ui | refactor | hotfix
risk:      L0 | L1 | L2
assurance: bounded | systemic        # 仅 risk: L2；分类时初选，完整设计复核
baseline:  spec | invariant | issue | confirmed-visual | none
visual:    not-applicable | regression | new-design
```

### Change Type

| 类型 | 定义 | 与风险的关系 |
|---|---|---|
| `feature` | 新增或改变已经确认的外部行为 | 风险由范围和技术边界决定 |
| `bug` | 现状偏离既有规格、不变量、ADR、问题记录或已确认基准 | 涉及认证、数据、PIT 等时仍是 L2 |
| `ui` | 视觉或交互调整 | `regression` 用于恢复基准，`new-design` 用于改变视觉意图 |
| `refactor` | 行为和外部契约不变的结构调整 | 风险由触及模块和数据边界决定 |
| `hotfix` | 生产环境紧急修复 | 可以压缩计划，不可跳过验证、回滚和事后记录 |

### Risk Level

| 等级 | 判定 | 流程强度 |
|---|---|---|
| `L0` | 文档、注释、无对外行为的微小修整；不触及数据、认证、UI、接口或共享约束 | 直接修改 + 适用静态检查；默认不创建 OpenSpec |
| `L1` | 单一功能或普通修复，无迁移、认证、数据源或跨服务变化 | proposal、规格增量、紧凑 design、tasks、verification |
| `L2` | 迁移、认证权限、数据源、PIT、回测口径、公共 API、跨服务、大范围重构或高风险安全修复 | 完整设计、保证档位要求的评审、L2 测试和回滚验证 |

如果无法确定等级，按更高一级处理。

### L2 Assurance Level

只有同时满足以下五项条件的 L2 才能选择 `assurance: bounded`：

1. 影响局限在一个可独立部署的服务、Provider 适配器或部署配置边界；
2. 不改变数据库 schema、数据语义、PIT、复权或回测口径；
3. 不改变权限模型、公共 API 或跨服务契约；
4. 可通过回滚代码或配置恢复，无需数据修复、重放或人工迁移；
5. 现有测试和验证能够覆盖改动边界。

任一条件不满足或分类存在争议时，必须使用 `assurance: systemic`。

- 档位在 proposal 分类阶段初选，由完整设计逐项复核。
- 完整设计或实施发现条件不再成立时，必须停止实施、升级为 `systemic`，补充实施前设计评审并重新取得用户确认。
- 实施开始后不得把 `systemic` 降为 `bounded`。
- 实施前确需降级时，必须停止规划、重新核对五项条件并取得用户确认。

### Baseline

| 基线 | 含义 |
|---|---|
| `spec` | 已有长期能力规格或本次新增行为规格 |
| `invariant` | 正确行为来自 `INV-*` 等不变量 |
| `issue` | 正确行为来自已记录的问题、复现步骤或技术债条目 |
| `confirmed-visual` | 正确外观来自用户确认的原型、截图或视觉基准 |
| `none` | 没有既有期望，本次需要形成新决策 |

`baseline: none` 不能直接支撑 bug 或 UI 回归；必须先补最小行为或视觉基线。存在既有约束时不能误填 `none`。

### Visual Impact

- `not-applicable`：纯后端、数据、文档或基础设施变更，且没有可见 UI 影响；proposal 必须说明原因。
- `regression`：恢复已确认视觉基准，仍需编码前用户视觉确认和前后截图。
- `new-design`：产生新的视觉意图，必须完成探索、用户确认、桌面/移动和明暗主题截图。

### Type-Specific Evidence

| 类型 / 场景 | 必填输入 | 完成证据 |
|---|---|---|
| `feature` | `AC-*`、范围和现有规格 | 验收测试、GREEN 结果、回归测试 |
| `bug` | 稳定复现、正确行为来源、根因 | 失败回归测试、修复后 GREEN、相关回归 |
| `ui` + `confirmed-visual` | 目标基准、受影响状态 | 用户视觉确认、前后截图、键盘/响应式/主题检查 |
| `ui` + `none` 或 `new-design` | 新视觉目标 | 视觉探索、用户确认、实现截图和交互验证 |
| `refactor` | 不改契约的边界说明 | 既有测试基线、无行为变化证据、审查结论 |
| `hotfix` | 症状、最小根因、影响面 | 复现或故障证据、修复验证、回滚方案、事后补全记录 |
| `L2 bounded` | 完整设计、五项条件复核 | 用户规划确认、实施后独立代码与风险评审、最新完整验证 |
| `L2 systemic` | 完整设计、系统性影响说明 | 实施前独立设计评审、实施后独立代码与风险评审、最新完整验证 |

### Classification Examples

- 规格要求每页 10 条，实际显示 20 条：`bug`，`baseline: spec`。
- 用户决定从 10 条改为 20 条：`feature`，`baseline: none`，更新规格。
- 已确认原型按钮应为蓝色，实际为灰色：`ui`，`baseline: confirmed-visual`，`visual: regression`。
- 用户希望改用绿色：`ui`，`baseline: none`，`visual: new-design`。
- `INV-*` 对应的 PIT 读取错误：`bug`，`baseline: invariant`，`risk: L2`；若改变数据口径则 `assurance: systemic`。
- 单个部署配置中的认证 Origin 修复：`risk: L2`，五项条件全满足时 `assurance: bounded`。

## Workflow

### Overview

```text
分类（L2 初选 assurance）
  ↓
形成最小行为契约（需要时）
  ↓
proposal + specs + design + tasks
  ↓
L2 systemic：实施前独立设计评审
  ↓
视觉门禁（仅可见变更）
  ↓
按计划连续实施 + TDD
  ↓
独立代码与风险评审 + 修复 findings
  ↓
最新完整验证
  ↓
用户验收
  ↓
用户单独确认归档
  ↓
视觉变更：提升 initial 基准 + 回写并验证 Atlas（仅可见变更）
  ↓
同步增量规格并归档
```

### Stage 1: Classify

输入：

- 用户请求；
- 相关规格、不变量、问题记录、ADR 和视觉基准；
- 影响模块与可见范围。

输出：

- `type`、`risk`、`baseline`、`visual`；
- L2 的初选 `assurance`；
- 是否需要 OpenSpec；
- 需要加载的领域 Skill。

完成条件：

- 能明确说明正确行为来自哪里；
- 没有用低风险标签规避认证、数据或视觉门禁；
- L0 判定无对外行为和可见后果；
- L2 已按五项条件初选保证档位，任何争议保留为 `systemic`。

### Stage 2: Clarify and Define the Contract

只有需求含糊、术语冲突、规格缺失或用户目标不明确时进入完整澄清。输出写入 proposal、能力规格、glossary 或 ADR。

- 用户可观察行为用 `AC-*` 或 OpenSpec scenario 表达；
- bug 必须有可复现的现状和既有期望；
- UI 回归必须引用确认基准；
- 新功能、多页面流程、权限或数据口径变化写紧凑 PRD-lite；
- 只有跨团队、多阶段或独立产品评审才生成完整 PRD。

### Stage 3: Plan the Change

默认产物：

1. `proposal.md`：Why、范围、元数据、AC、影响和视觉状态；
2. `specs/<capability>/spec.md`：外部行为和场景；
3. `design.md`：决策、替代方案、风险、兼容性、迁移和回滚；
4. `tasks.md`：任务、文件、失败测试和验证命令。

设计深度：

- L1 无新决策时，`design.md` 只记录“无新增技术决策”及影响边界；
- L1 有取舍时，用简短决策表；
- L2 必须包含完整替代方案、失败模式、兼容性和回滚方式；
- L2 完整设计必须逐项复核 bounded 五项条件；
- `docs/superpowers/specs` 只有需要补充完整独立方案时生成。

任务粒度：

- 一个任务是一个可独立验证的纵向切片；
- 任务必须关联 AC；
- 行为任务必须写明失败测试和验证命令；
- 文档任务写明内容校验、链接检查或 OpenSpec 校验；
- 不在任务中复制完整实现或大段测试代码。

### Stage 4: Visual Design Gate

任何新增或修改页面、组件、可见状态、交互、信息层级、加载/空/错误/部分成功、响应式或明暗模式都必须执行。

1. 判断 `visual: regression` 或 `new-design`；
2. 从确认基准复制到 `docs/design/prototypes/explorations/`，不覆盖历史原稿；
3. 覆盖受影响状态、桌面/移动和浅色/深色；
4. 生成真实截图并处理控制台、图片、溢出和对比度问题；
5. 用户确认后，才能加入生产代码实施任务。

视觉门禁可引用 L2 完整设计，但视觉确认和计划确认仍是两个不同决策。`assurance: bounded` 不豁免视觉门禁。

### Stage 5: Implement

- 先读取 `tasks.md` 当前任务和相关规格；
- 行为代码先写失败测试并观察 RED，再写最小实现取得 GREEN；
- L1 的多个低风险任务和 L2 的已批准任务可以连续执行；
- 前端加载 `frontend` 和 `vercel-react-best-practices`，UI 加载 `oil-ui` 和 `ui-design`；
- 后端加载 `backend`，数据边界加载 `database`；
- 计划需要改变接口、范围、保证档位或风险等级时停止并请求确认。

### Stage 6: Review and Verify

按风险和保证档位选择：

- L1：自检 + 适用测试 + 最终验证；
- L2 bounded：实施后独立代码与风险评审 → 修复 findings → 最新完整验证；
- L2 systemic：实施前独立设计评审 → 实施 → 实施后独立代码与风险评审 → 修复 findings → 最新完整验证；
- UI：视觉回归和行为回归；
- 数据：迁移、PIT、数据质量和回滚；
- 完成前必须运行最新完整命令。

所有 L2 的 `changes-required` 必须在请求用户验收前清零。评审后只要修改代码或配置，旧验证结果即失效，必须重新运行最新完整验证。

### Stage 7: Accept and Archive

- `verification.md` 给出 AC 到证据的映射；
- `verification.md` 记录 L2 bounded/systemic 的评审结论、日期和 findings 处理结果；
- 用户先验收实施和验证结果；
- 用户单独确认后才能归档；
- `visual: regression | new-design` 的变更在归档前，必须将用户验收的最终稿提升到
  `docs/design/prototypes/initial/`，并更新 `docs/design/prototypes/atlas/index.html`
  的对应页面条目；
- Atlas 条目必须关联 change 名称、最终基准稿和关键截图或截图索引，并从 Atlas 单入口
  打开验证链接可用；验证结果写入 `verification.md`；
- 最终基准、Atlas 条目或验证证据缺失时，必须停止归档；用户确认归档不能替代视觉同步；
- `visual: not-applicable` 的变更不要求更新 Atlas，但 proposal 必须说明无可见 UI 影响；
- 归档时同步增量规格到 `openspec/specs/`。

## Artifacts

### Default OpenSpec Pack

| 产物 | 内容 | 不应包含 |
|---|---|---|
| `proposal.md` | 元数据、Why、范围、非目标、AC、影响、视觉状态 | 详细架构、完整任务步骤 |
| `specs/*/spec.md` | 外部行为、输入输出、错误场景 | 文件清单、实现代码 |
| `design.md` | 决策、替代方案、风险、兼容性、迁移、回滚、systemic 设计评审 | proposal 重复内容 |
| `tasks.md` | 唯一任务清单、AC 映射、测试与验证命令 | 第二份完整技术设计 |
| `verification.md` | 命令、结果、AC 证据、L2 实施后评审、截图、未覆盖项 | 重新声明需求 |

### Conditional Artifacts

| 产物 | 使用条件 | 约束 |
|---|---|---|
| `docs/superpowers/specs/*-design.md` | 需要补充完整独立方案 | 链接 proposal/spec，不成为平行事实源 |
| `docs/superpowers/plans/*.md` | 多模块、长任务、并行 Agent 或每任务独立审查 | `tasks.md` 仍是唯一进度清单 |
| `.superpowers/sdd/*/progress.md` | 选择 `executing-plans` | 与 `tasks.md`、`verification.md` 保持一致 |
| `docs/adr/*.md` | 难回滚、非显然、存在真实取舍 | 只记录长期决策，不记录单次任务 |

### Evidence Rules

- 失败测试保留任务级 RED/GREEN 摘要；
- 长日志写入临时文件，只保留命令、结果计数和失败摘要；
- bounded L2 的实施后独立评审写入 `verification.md`；
- systemic L2 的实施前独立设计评审写入 `design.md#Review Result`，实施后评审写入 `verification.md`；
- 评审修复后的最新完整验证必须晚于最后一次修改；
- 截图和原型链接放 verification 或 design，不复制到多个文档；
- 已归档历史变更不按 v3 重写。

## Confirmation Model

### Default Checkpoints

1. **规划确认**：范围、规格、设计、风险、保证档位和 tasks 一次评审；
2. **实施授权**：规划确认后允许按 `tasks.md` 连续执行已批准任务；
3. **最终验收**：实现、独立评审和最新验证完成后由用户验收；
4. **归档确认**：用户单独确认归档。

计划确认和实施授权可以由用户同一句话完成；视觉确认、最终验收和归档确认不能由规划确认自动推导。

### Hard Stops

遇到以下情况必须停止：

- 范围、AC 或产品目标变化；
- 新的架构或产品决策；
- 认证、权限、安全边界变化；
- 数据源、PIT、回测口径或迁移变化；
- L2 bounded 五项条件不再全部成立，或需要变更保证档位；
- 新增依赖、外部服务或破坏性操作；
- 新的视觉方向、可见状态或交互；
- 测试失败且不能按已批准方案处理；
- 实施计划需要改变接口、风险等级或任务结构；
- 任一 L2 评审仍有未清零的 `changes-required`；
- 有视觉影响的变更缺少最终基准、Atlas 条目或 Atlas 验证证据。

### Non-Stop Conditions

以下情况不要求逐项确认：

- 在已批准任务内补测试；
- 修复局部实现错误且不改变接口和范围；
- 按现有 TDD 循环从 RED 到 GREEN；
- 处理独立评审 findings 且不扩大范围或改变保证档位；
- 运行计划中的验证命令；
- 更新任务勾选和验证证据。

## Skill Routing Matrix

### Status Semantics

- `required`：进入对应范围时默认必须使用；
- `conditional`：只在明确触发条件满足时使用；
- `optional`：辅助能力，仅特殊情况使用；
- `not-in-workflow`：已安装但不再属于 v3 流程。

| Skill | 职责 | 输入 | 输出 | 使用阶段 | 触发条件 | 状态 |
|---|---|---|---|---|---|---|
| `backend` | 实现后端 API、auth、worker 和观测边界 | API、权限、安全和数据约束 | 后端代码与测试 | 实施、审查 | 后端变更 | `conditional` |
| `brainstorming` | 比较方案、发现约束并形成设计 | 含糊目标或非显然取舍 | 方案、决策和风险 | 规划 | L2 或非显然设计 | `conditional` |
| `code-review` | 检查正确性、安全、数据安全和测试缺口 | change、规格、调用方 | 分级 findings | 审查 | L2 或高风险变更 | `conditional` |
| `code-simplifier` | 在不改变行为下优化可读性 | 已通过测试的实现 | 精简代码 | 实施后 | 复杂实现需要整理 | `optional` |
| `database` | 设计数据结构、迁移、同步和 PIT 读写 | 数据模型与读取约束 | schema、迁移和查询方案 | 规划、实施 | 数据模型或读取行为变化 | `conditional` |

## Quality Gates

### Change Admission

- 元数据齐全；
- 变更类型和基线可解释；
- L0 没有隐藏的接口、数据、认证或可见行为；
- L2 已初选 `assurance` 并识别迁移、安全和回滚。

### Specification

- 新增或改变外部行为必须更新能力规格；
- bug 必须指向既有期望；
- UI 回归必须指向确认基准；
- 同一事实不在 proposal、spec 和 design 之间重复。

### Design and Review

- L1 明确“无新增技术决策”或列出简短决策；
- L2 完成替代方案、风险、兼容性、回滚和五项条件复核；
- bounded L2 不要求实施前独立设计评审，但必须完成实施后独立代码与风险评审；
- systemic L2 必须完成实施前设计评审和实施后代码与风险评审；
- 任一 `changes-required` 未清零时不得进入下一阶段，也不得请求验收。

### Visual

- 所有可见变更都有用户视觉确认；
- `regression` 不豁免确认；
- 截图覆盖受影响状态、桌面/移动和明暗主题；
- `bounded` 不豁免视觉门禁；
- `visual: regression | new-design` 的变更归档前必须有最终 `initial/` 基准、Atlas 条目
  和可访问性验证；
- 不适用时 proposal 写明具体原因。

### Implementation

- 行为代码先失败后通过；
- 任务只按 `tasks.md` 推进；
- 风险、范围或保证档位变化触发硬停；
- 领域 Skill 的项目约束优先于通用 Skill。

### Verification and Archive

- `verification.md` 关联 AC、命令、评审和证据；
- 评审修复后的最新完整命令通过后才能请求验收；
- 用户验收与归档确认分离；
- 有视觉影响的变更在移动 change 目录前完成 Atlas 回写与浏览器验证；
- 归档后同步规格，失败或未覆盖项必须明确记录。

## Known Costs and Failure Modes

### Trade-offs

- 需要先判断类型、风险、L2 保证档位和基线；
- bounded L2 仍需完整设计、规划确认、实施后独立评审和回滚证据；
- systemic L2 仍保留双评审；
- 视觉门禁仍然不能自动化跳过；
- 批量执行要求 Agent 在硬停边界保持敏感。

### Failure Modes

- **L0 滥用**：把有可见行为、API 或数据影响的变更当作 L0。
- **bug 伪装**：没有既有期望却标记为 bug，绕过产品决策。
- **风险降级**：把认证、PIT 或迁移修复当成普通 bug。
- **bounded 滥用**：忽略 schema、数据语义、权限、公共 API、跨服务或回滚条件。
- **评审后证据过期**：评审修复后沿用旧测试结果。
- **视觉豁免**：把 UI 回归当作纯样式调整，跳过用户确认。
- **Atlas 滞后**：实现和验收完成，却只保留探索稿，没有更新当前设计 Atlas。
- **平行事实源**：同时维护 `tasks.md`、Superpowers plan 和 ledger 而不建立映射。
- **归档提前**：验证或用户验收完成就自动归档。

### Mitigations

- 元数据写在 proposal 顶部，任务和 verification 引用相同 AC；
- 不确定风险时升级到 L2；有分类争议时使用 `assurance: systemic`；
- `baseline: none` 阻止未经决策的 bug 修复；
- 评审后发生任何修改必须重新运行最新完整验证；
- 视觉门禁检查 `visual` 和用户确认记录；
- 归档 Skill 在移动 change 前检查最终基准、Atlas 条目和浏览器验证证据；
- 条件文档只作为补充，OpenSpec 始终是控制面；
- 归档必须单独确认。
