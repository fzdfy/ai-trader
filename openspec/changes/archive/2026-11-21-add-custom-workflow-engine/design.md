# Design

## Context

当前工作流只有前端占位页，没有定义、版本、调度或运行记录。现有选股与回测在请求内完成长计算，AI 因子迭代通过 `job_run` 异步执行，复盘生成依赖 Agent；项目已经安装 `pg-boss`，但只有 feature worker 骨架。行为契约见 `specs/workflow-orchestration/spec.md` 与 `specs/workflow-authoring-ui/spec.md`。

## Goals / Non-Goals

**Goals:**

- 独立于同步任务，建立可版本化的用户工作流、DAG 执行和审计链路。
- 复用现有业务逻辑，不通过服务端 HTTP 自调用绕过身份和错误边界。
- 让配置、调度、执行和 UI 状态使用同一个发布版本。

**Non-Goals:**

- 不提供循环、条件节点或任意代码节点。
- 不提供公开分享、团队协作或跨用户执行。
- 不支持从失败节点恢复执行；取消或失败后重新运行整个版本。
- 不把完整选股、回测或复盘数据复制进工作流表。

## Decisions

### 数据模型与版本

新增四张表：

- `workflow_definition`：创建者、名称、描述、当前草稿图、当前发布版本、启停和归档时间。
- `workflow_version`：不可变图 JSON、触发类型、触发配置和递增版本号。
- `workflow_run`：工作流版本、触发来源、状态、当前节点、取消请求、上下文摘要、开始/结束时间。
- `workflow_node_run`：节点输入摘要、输出摘要、状态、错误和耗时。

工作流默认私有，所有查询必须绑定 Better Auth 会话中的用户，不接受客户端传入的用户 ID。归档不删除定义和运行记录。运行和节点历史保留 90 天，由维护任务清理。

替代方案是把图直接存在定义表。该方案会让历史运行随编辑漂移，无法审计，因此不采用。

### DAG 与类型化上下文

服务端使用 Zod 校验图结构：恰好一个触发器、无循环、所有动作节点可达、端口类型合法。执行上下文只包含：

- `symbols: string[]`
- `tradeDate: YYYY-MM-DD`
- 节点摘要映射

股票池和选股输出 `symbols[]`；回测消费 `symbols[]`，最多 50 只，逐只执行后汇总；复盘和 AI 因子迭代只消费自身配置与交易日，不允许任意 JSON 变量。

### 队列、调度与同步事件

复用现有 `pg-boss`：

- API 创建运行后将 `workflow-run` 任务发送到队列。
- 新增独立 workflow worker，消费 `workflow-run` 并执行 DAG。
- 已发布定时工作流注册为 pg-boss schedule，统一使用 `Asia/Shanghai`；仅交易日执行。
- 同步 worker 在指定模块成功后调用共享触发函数，将匹配的已发布工作流加入运行队列。

替代方案让 API 进程直接执行节点。它会在服务重启时丢失运行且无法限制并发，因此不采用。

### 节点执行复用现有服务

将选股、回测、复盘生成和 AI 因子迭代的路由内逻辑提取到可复用服务。节点执行器只调用服务并使用明确的用户身份、AbortSignal 和超时。现有 API 路由改为调用同一服务，避免维护两套逻辑。

- 股票池节点读取自选股、当日落库选股池或手动代码。
- 选股节点复用策略选股服务。
- 回测节点逐标的调用回测服务，汇总成功/失败数量和摘要。
- 复盘节点调用复盘生成服务，保存 `review_daily.date` 引用。
- AI 因子迭代节点创建现有迭代任务，保存 `job_run.id` 引用并等待终态。

### 并发、失败与取消

数据库部分唯一索引保证每个工作流最多一个活动运行。触发器遇到活动运行时写入 skipped 记录并结束。节点失败立即停止下游；同层分支可以并行执行。

取消采用 best-effort：写入 `cancel_requested_at`，执行器在每个节点边界检查并停止调度后续节点。已发出的量化或 Agent 请求不强制终止，但结果不进入后续上下文。

### 工作流画布

前端新增 `@xyflow/react`，提供节点面板、拖拽、连线、删除、缩放、适配画布、配置抽屉和撤销/重做。触发器与动作节点从同一端口类型系统生成，非法连接在客户端即时拒绝，服务端发布时再次校验。

移动端采用纵向画布和覆盖式配置抽屉，避免整页水平滚动。键盘用户可通过节点列表和配置抽屉完成选择、编辑、删除和发布。

### API 与页面

API 提供工作流列表/详情、保存草稿、发布、启停、归档、手动运行、取消和运行历史。

页面：

- `/home/workflows`：行式列表和最近运行。
- `/home/workflows/new`：新建草稿。
- `/home/workflows/$workflowId`：画布编辑器。
- `/home/workflows/runs/$runId`：节点时间线和结果摘要。

工作台“今日工作流”读取当前用户今天的运行摘要，显示名称、触发时间、当前步骤、状态和耗时；没有运行时显示空状态。

### 结果保存与清理

节点结果保存输入摘要、输出摘要和业务引用；完整 JSON 设置统一大小上限，超限时只保留摘要与引用。维护任务每天清理超过 90 天的运行和节点记录。

## Risks / Trade-offs

- **长业务请求占用 worker**：选股、回测和复盘可能运行数分钟，单 worker 并发受限。通过 pg-boss 并发上限、节点超时和 50 只回测上限控制。
- **取消不能终止在途请求**：接口会明确提示在途步骤可能完成，仅保证后续节点不启动。
- **服务提取影响现有 API**：提取必须保持原请求/响应契约，并用现有功能测试和新增工作流节点测试共同覆盖。
- **动态调度与多实例重复触发**：pg-boss schedule 使用唯一名称，执行入口通过数据库活动运行唯一约束兜底。
- **图数据演进**：版本 JSON 保存 `schemaVersion`，未来节点参数变化通过迁移函数读取旧版本。

## Migration Plan

1. 新增数据库表、迁移和索引。
2. 提取业务服务并让现有 API 路由继续通过回归测试。
3. 增加工作流 API、队列 worker、调度器和同步完成触发。
4. 上线列表、画布编辑器和运行详情，再将工作台占位改为真实运行摘要。
5. 回滚时关闭 workflow worker 和新页面入口；旧业务 API 不受影响，新增表保留。
