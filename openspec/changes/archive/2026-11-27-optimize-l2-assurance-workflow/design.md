# Design

## Context

动机和用户可见行为见 [proposal.md](./proposal.md) 与
[spec.md](./specs/ai-coding-workflow/spec.md)。

| 当前事实 | 约束 |
|---|---|
| [v2.md](../../../docs/standards/sdd/v2.md) 是当前流程，所有 L2 都要完整设计和独立评审 | v1、v2 是冻结历史，不能改写历史语义 |
| 局部认证配置 `simplify-auth-origin-config` 只有 4 个 AC、6 个任务 | 仍需完整设计、独立评审和全部验证 |
| 系统性信号矩阵有 14 个 AC、58 个任务、557 行外部设计 | 设计评审与实施后评审都能发现不同层级风险 |
| OpenSpec、`AGENTS.md`、`development-workflow.md` 和 `openspec/config.yaml` 共同描述现行流程 | 改规则时必须避免平行事实源 |

本变更本身跨项目入口、OpenSpec 行为规格和长期标准，按 `risk: L2`、
`assurance: systemic` 规划，需要实施前独立设计评审。

## Goals / Non-Goals

**Goals:**

- 让局部 L2 保留 L2 风险分类，同时去掉实施前重复的设计评审。
- 让系统性 L2 继续通过实施前设计评审拦截架构、权限、数据和迁移风险。
- 使用可复用的确定性条件区分 `bounded` 与 `systemic`，避免按主观工作量判断。
- 保持验收、验证、回滚、视觉和归档门禁不变。

**Non-Goals:**

- 不把任何认证、数据、PIT、迁移或跨服务变更降为 L1。
- 不改变默认 OpenSpec 五件套，也不在本变更中压缩 bounded L2 文档数量。
- 不改变视觉门禁、TDD、用户验收或归档确认。
- 不迁移已启动或已归档 change。
- 不新增 L3 风险等级。

## Decisions

### 1. 保留 L2，新增保证档位

每个 L2 change 在现有 `type/risk/baseline/visual` 后增加：

```text
assurance: bounded | systemic
```

L0/L1 不要求该字段。风险等级回答“影响是否严重”，保证档位回答“需要哪种审查
时序”，两者不能互相替代。

替代方案是新增 L3。该方案会让全仓风险术语和历史 change 迁移，且用户真正需要的
只是同一 L2 内部的审查差异，因此不采用。

### 2. 使用全部条件判定 bounded

只有同时满足以下条件才能选择 `bounded`：

1. 影响局限在一个可独立部署的服务、Provider 适配器或部署配置边界；
2. 不改变数据库 schema、数据语义、PIT、复权或回测口径；
3. 不改变权限模型、公共 API 或跨服务契约；
4. 可通过回滚代码或配置恢复，无需数据修复、重放或人工迁移；
5. 现有测试和验证能够覆盖改动边界。

任一条件不满足，或分类存在争议时，默认 `systemic`。

L2 在 proposal 分类阶段初选档位，完整设计复核五项条件。完整设计或实施过程中发现
任一条件不再成立时，必须停止当前实施、升级为 `systemic`，补充实施前设计评审并
重新取得用户规划确认。

实施开始后不得把 `systemic` 降为 `bounded`。实施前确需降级时必须停止规划、
重新核对五项条件并取得用户确认。

替代方案是按 diff 行数或任务数量区分。行数不能反映数据语义、权限和回滚复杂度，
因此不采用。

### 3. bounded 将独立设计审查合并到实施后风险审查

`bounded` 的评审时序：

```text
完整 design + tasks
  ↓
用户规划确认
  ↓
实施 + TDD
  ↓
独立代码与风险评审
  ↓
修复 findings
  ↓
最新完整验证
  ↓
用户验收
```

实施后审查必须同时检查规格、设计决策、实现、调用方、测试、数据/权限边界和回滚
证据。评审结果写入 `verification.md`，因为它是最终证据汇总，不再要求实施前的
`design.md#Review Result`。评审后只要发生代码或配置修复，旧验证结果即失效；
`changes-required` 清零并重新运行最新完整验证后才能请求用户验收。

替代方案是彻底取消独立评审或完全由作者自查。两者都会移除 v2 保留下来的核心风险
边界，不采用。

### 4. systemic 保留双评审

`systemic` 继续要求：

- 实施前独立设计评审写入 `design.md#Review Result`；
- 实施后独立代码与风险评审写入 `verification.md`；
- 两类评审各自存在 `changes-required` 时不得进入下一阶段。

实施后评审修复 findings 后同样必须重新运行最新完整验证。

替代方案是让 systemic 也只做实施后评审。但跨服务、权限模型、数据口径和迁移的
错误一旦落到代码或数据中，回滚成本明显高于设计阶段修正，因此不采用。

### 5. 本次只优化审查时序

默认五件套、TDD、视觉门禁、验收和归档不变。先单独度量保证档位带来的流程收益；
如果 bounded 的文档成本仍显著，再另开 change 评估三件套方案。

替代方案是在同一变更中同时压缩产物数量。评审时序与文档数量的失败模式不同，
合并会降低验证信号的可归因性，因此不采用。

### 6. v3 采用增量版本

新增 `v3.md` 和 `v2-to-v3.md`，将 v2 标记为历史。`AGENTS.md` 和短入口只保留
新字段、硬门禁和版本链接，Skill 明细仍只维护在版本正文。

替代方案是直接改写 v2。仓库版本契约要求未来版本新增文件，因此不采用。

## Risks / Trade-offs

- **bounded 误判**：把数据语义或跨服务变化误当成局部配置 → 使用五项全满足规则，
  任一争议默认 `systemic`，并在独立代码与风险评审中检查实际影响面。
- **实施前少一道门**：bounded 到实施后才发现架构问题 → 完整 design、用户规划
  确认和回滚条件仍是前置输入；发现范围扩大时立即升级 `systemic` 并停止实施。
- **评审后证据过期**：代码按评审意见修复但沿用评审前测试结果 → 任何修复后必须
  重新运行最新完整验证，并在 `verification.md` 记录评审后运行时间。
- **评审术语漂移**：`bounded` 被理解为低风险或可少测试 → 文档统一写成“保证档位”
  而不是风险等级，并明确所有 L2 门禁保留。
- **新增字段增加分类成本**：每个 L2 多一个判断 → 五项条件可快速排除，且只作用于
  L2，不影响 L0/L1。
- **流程文档多处同步**：入口和配置可能再次分叉 → v3 是唯一完整正文，其他文件只
  保留短规则和链接，并通过静态搜索与 OpenSpec 严格校验验证一致性。

## Migration Plan

1. 创建 v3 正文，将 bounded/systemic 分类、审查时序和证据位置写入唯一完整流程。
2. 创建 v2→v3 迁移说明，记录保留项、变化项、回滚和历史兼容。
3. 更新版本索引、开发工作流短入口和 `AGENTS.md`。
4. 更新 `openspec/config.yaml` 的元数据、设计和验证规则。
5. 更新 `docs/glossary.md`，区分风险等级与 L2 保证档位。
6. 验证主规格保持待归档状态；归档时再同步增量规格，并运行静态检查、链接检查、OpenSpec validate 和 diff check。
7. 存量 change 继续使用启动时版本；只有新 change 默认使用 v3。

回滚：

- 将版本索引、`AGENTS.md`、短入口和 OpenSpec 配置恢复到 v2；
- 保留 v3 和迁移文件作为审计记录；
- 不重写本变更生效后已形成的验证证据。
