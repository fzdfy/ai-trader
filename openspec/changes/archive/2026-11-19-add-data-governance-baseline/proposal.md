# Proposal

## Why

平台已经具备数据源注册、同步依赖、基础新鲜度和受控运维，但数据责任、资产等级、契约、质量结果、事故、血缘和外部来源标准版本仍分散或缺失。随着数据表和来源规范持续演进，需要先建立可执行的治理基线，防止数据目录漂移、来源静默变化和不可信数据进入研究结论。

## What Changes

- 建立覆盖全部数据资产的治理目录，记录数据域、Owner、Steward、Operator、Tier、分类、契约、SLA、保留期限和血缘。
- 为 Tier 0 数据定义质量规则，在同步后保存质量结果，并对回测、选股和个股分析执行质量门禁。
- 引入数据事故的创建、确认、解决和审计闭环。
- 固定 `a-stock-data` 来源标准版本与 checksum，由系统 Worker 检测新版本并创建 Work Task；正式升级仍通过 OpenSpec。
- 在现有数据管理区域增加“治理”入口，展示资产、质量规则与结果、来源标准版本和数据事故。
- 保持治理静态元数据为代码事实源，数据库只保存质量结果、事故、告警、版本事件和操作审计。

## Product Requirements

### Users

- `super_admin`：查看完整治理目录、质量结果、来源标准版本、数据事故，并执行受控运维。
- `user`：只看到不敏感的聚合数据可信度状态，不看到内部表、来源、事故或质量细节。

### Success Metrics

- 所有已登记数据资产都有数据域、责任角色、Tier、分类和消费边界。
- 所有 Tier 0 资产都有可执行质量规则和明确门禁策略。
- 任一研究结果都能追溯到数据资产、来源标准版本、同步任务、质量结果和责任人。
- `a-stock-data` 发生版本变化后，系统能在 24 小时内检测并生成审阅 Work Task。

### Non-Goals

- 不建设企业级合规、人事数据治理或审批平台。
- 不提供后台编辑静态治理元数据或任意 SQL。
- 不自动采用外部 Skill 新版本。
- 不在本期实现全自动字段级 SQL 解析、自动回补或自动重建。
- 不把产品 Workflow 用作平台级治理调度器。

### Acceptance Criteria

- 数据治理目录与仓库 Schema、Provider 注册表和同步任务保持一致，并覆盖全部资产。
- Tier 0 数据存在严重未解决事故时，新的回测、选股和个股分析被明确阻止。
- `a-stock-data` 固定版本、来源、checksum 和能力映射可查询。
- 来源标准检测任务、质量检查和事故状态变化均可审计。
- 普通用户无法通过页面或 API 获取敏感治理详情。

## Capabilities

### New Capabilities

- `data-governance-catalog`: 定义数据域、资产责任、等级、分类、契约、SLA、保留和血缘的治理目录。
- `data-quality-control`: 定义并执行质量规则，保存质量结果，并据此阻止或警告研究任务。
- `source-standard-governance`: 固定外部来源标准版本，检测升级并管理兼容性评审流程。
- `governance-review-tasks`: 为来源标准变化等治理事件创建最小可复用的审阅 Work Task。
- `data-governance-console`: 在现有数据管理中提供治理资产、质量、来源版本和事故的只读运营视图。

### Modified Capabilities

无。本变更新增治理能力，不改变现有 `preline-workbench-ui` 的通用视觉与可访问性要求。

## Impact

- Web：数据管理区域新增治理入口和页面，普通用户仍只看到聚合状态。
- Server：新增治理目录读模型、质量规则执行与门禁、来源标准检测、事故服务和 API。
- Database：新增质量结果、数据事故及必要的来源版本事件记录。
- Quant：复用现有 Provider、能力健康和数据读取逻辑，不改变 `load_kline` 契约。
- Worker：新增来源标准巡检和同步后质量检查任务，复用 `job_run` 与 Work Task。
- Docs：更新数据治理标准、数据链路文档、术语和实施验证记录。
